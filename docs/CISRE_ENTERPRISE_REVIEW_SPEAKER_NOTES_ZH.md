# CISRE 企业统一 SRE 平台评审讲稿

对应材料：`CISRE_ENTERPRISE_OPS_PLATFORM.pptx`  
建议时长：25–30 分钟；讨论与答疑另留 15 分钟。  
核心目的：邀请各基础设施团队在同一个 CISRE Harness 上交付领域插件与 Skills，共享企业级运行、治理和安全能力，不再重复建设 Agent 底座。

## 第 1 页｜让基础设施自解释、可安全自愈、可证明恢复

今天我想讨论的不是再做一个聊天机器人，而是把我们分散在各团队、各值班人员手里的运维经验，变成可以被组织复用的能力。CISRE 的目标可以概括成三句话：基础设施能够解释发生了什么；任何变更都在安全边界内；最终必须拿真实状态证明问题已经恢复。

当前 5.6.0 已把插件服务、Skill、Agent 编排、审批、执行和恢复验证放进同一条生产链路。Kubernetes 是第一个跑通的领域；数据库、VM、存储、中间件、云和网络不是要重新各做一套平台，而是通过统一插件合同加入。

转场：先看为什么现有方式无法满足企业 SRE 的完成标准。

## 第 2 页｜现在已有可落地闭环，下一步是团队共建

这页给出结论。第一，Kubernetes 已有真实取证、动态 Skill、逐项审批、变更回读和新 Pod 验证。第二，CISRE Harness 已具备可调用插件服务、能力模式、事件溯源、Trace、分支和完整插件工程导出。第三，现在最缺的不是另一个通用框架，而是各领域团队把自己的专业知识做成插件和 Skills。

我们邀请的不是“来帮平台组改核心代码”，而是每组认领本领域合同：Provider 提供事实，Skill 提供处置经验，类型化动作说明允许做什么，Verifier 说明什么才算恢复。公共能力由 CISRE 维护，领域能力由最懂业务的人维护。

转场：为什么一定要统一“完成”的定义？

## 第 3 页｜三种旧方式都无法证明业务真正恢复

过去常见三种做法都有价值，但都缺一块。监控能告诉我们有问题，却通常不能安全执行；模型能给建议，却可能没有真实证据；脚本能改资源，却很难统一审批、回滚、爆炸半径和成功判据。

最关键的问题是，我们经常把 API 返回 2xx、脚本退出码 0，甚至模型说“已修复”，当成完成。对 SRE 来说这些只是过程证据。真正的完成应该是：目标资源确实变了，新实例确实接管，错误信号消失，并且稳定窗口内没有复发。

常见质疑：现有自动化平台也能执行脚本。回答是，CISRE 的差异不在“能执行”，而在证据、审批、同目标回读、恢复证明和成效记录被强制组成一个不可跳过的协议。

## 第 4 页｜统一完成语义：恢复才算完成

SRE Run 和 AI 巡检共用同一内核：上下文进入后先取证，再由模型和算法做根因判断，动态选择最匹配的主 Skill；只有必要时才串行组合多个 Skill。所有真实动作必须变成类型化变更，计算爆炸半径并逐项人工审批。

执行完成后，Verifier 不相信执行器的口头结果，而是从同一通道、同一集群、同一资源重新读取。只有满足新状态、稳定窗口和业务判据，Records 才记录“已解决”。失败就保留证据、换策略、重新审批，持续到恢复或人工中断。

转场：下面看目前已经能交付的能力，而不是未来设想。

## 第 5 页｜CISRE 5.6.0 已具备的生产能力

当前平台已经有集群纳管、Rancher 与 kubeconfig 双通道、SRE Run、AI 巡检、拓扑影响、Skill 库、插件中心、Trace、Records 和成效统计。核心运维能力不是页面各写一套：对话和巡检都调用同一个诊断、路由、审批、执行和验证内核。

Skill 路由以实时证据排序，不会因为一个 Workload 被刷新几十次就把每次候选匹配都算成调用。只有实际执行的 Skill 才进入调用统计；成功率也以最后是否证明恢复为准。

需要如实说明：Kubernetes 已完成真实闭环实现与 275 项回归；其他领域已经有合同、脚手架、治理接口和 UI，但厂商连接与领域动作仍需要相应团队交付，平台不会用模拟数据伪装成已纳管。

## 第 6 页｜权限类 CrashLoop：从日志根因到验证闭环

这是我们反复打磨的真实案例。系统优先读取当前 Pod 的 ERROR/WARNING 和状态；当前容器没有可用日志时，才使用 previous 日志辅助诊断。看到 `not writable`、`unable to open database file` 等信号后，模型结合 Workload、挂载和 securityContext 证据匹配卷权限恢复 Skill。

策略不是把某个固定 UID 写死。先读取镜像和 Workload 的现有身份，尝试最小权限的 fsGroup、runAsGroup 或目录属主方案；证明无效后才升级到 root 方案，并明确写成 `runAsUser: 0`、`runAsGroup: 0`、`runAsNonRoot: false`。每个阶段都是新补丁、新审批、新验证。

5.6.0 进一步修正了闭环：当前日志接口返回 400 时，如果新 revision Pod 已 Ready、rollout 收敛、重启稳定且业务探针通过，可以作为恢复证明；旧 Pod 的 BackOff Event 不会永久阻塞健康的新 Pod，但实时复发仍会重新打开故障链。

## 第 7 页｜可信内核稳定，领域能力通过插件扩展

架构分四层。体验层是 SRE Run、巡检、拓扑、Skill、插件和成效；插件控制面负责能力注册、可调用服务、Agent Loop、编排、审批以及 Event/Trace；受控执行面只接受类型化动作，执行爆炸半径、审批、执行、回读和验证；事实层连接 Rancher、kubeconfig 以及七个领域的 Provider。

内核通过 Kernel Port v1 固定 Event Journal、Lease、Job Queue 和 Snapshot 的语义。今天可以用单机实现，业务量增长后可替换成数据库、消息队列和分布式租约，调用合同和完成语义不变。这样团队可以扩展能力，平台也能横向扩容，而不需要推倒重来。

常见质疑：插件化是不是仍然要改核心？回答是，核心只在新增通用治理语义时演进；新增厂商、资源类型、诊断方式或 Skill 不需要加核心 `if/else`，通过插件 Manifest 的 provides/requires 与类型化动作目录接入。

## 第 8 页｜借鉴通用 Harness，生产控制权留在 CISRE

我们认真借鉴了 DeepSeek Harness 的插件化、依赖注入、能力组合、事件驱动和会话溯源设计，但不直接把一个通用 Agent Harness 当成生产运维控制面。官方项目当前仍是 Developer Preview，定位是通用 Agent 组合；而企业 SRE 还必须绑定真实资产、凭据边界、爆炸半径、逐项审批、同目标回读、恢复验证和成效审计。

我们的选择是复用成熟思想，避免重复造通用 Agent 轮子；同时把生产 mutation 权限牢牢放在 CISRE 的执行门禁内。插件和子 Agent可以发现、分析、提出方案，但不能绕过审批直接改生产。

参考：DeepSeek Harness 官方仓库与架构文档分别为 <https://github.com/deepseek-ai/deepseek-harness> 和 <https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/architecture.md>。

## 第 9 页｜Harness 组合能力已落入 CISRE 生产运行时

这一页不是概念映射，而是运行时落点。插件通过 provides、requires、scope 和 priority 声明服务；Capability Registry 选择真实可调用 Provider。Profile、Bundle、Patch 让相同能力在本地、沙箱和生产使用不同实现，不需要复制两套业务代码。

事件支持 observe、serial、parallel 和 waterfall；会话支持 replay、fork、resume 和 tombstone；Agent Loop 有步骤边界、Owner Job 与上下文压缩。子 Agent 编排默认只读，任何 mutation 都回到主审批链。Trace 把 Context、Skill、Plugin、Tool、Approval、Change 和 Verify 放进同一时间线。

重要边界：我们没有把外部框架代码原样塞进生产，而是按 CISRE 的安全模型实现兼容的能力语义，并用对照矩阵记录已实现、部分实现和规划项。

## 第 10 页｜团队只维护插件，核心负责编排与治理

插件首先是一份可验证声明：ID、版本、Owner、Domain、Agent、Provides、Requires、Events、Scope、Priority、Permissions 和 Runtime Mode。运行时自动完成依赖解析、Provider 选择、加载、卸载、热重载、审计和资源释放。

安全边界同样写进合同。外置 Provider 默认独立容器且只读，凭据只用 Secret 引用或工作负载身份。需要 mutation 时，插件只能提出类型化意图，由 CISRE 展示差异、计算风险、等待审批、调用受控执行器并验证。

前端现在可以一键下载完整工程，不只是一个 JSON：包括 Provider、Skill、合同测试、Dockerfile 和 Kubernetes YAML。各组不需要复制主仓库，也不需要理解全部核心实现。

## 第 11 页｜插件开发、调用条件与安全边界一目了然

插件中心要解决两个问题：使用者能看懂，开发者能起步。每个插件详情展示它什么时候被调用、提供和依赖什么服务、作用域和权限、安全边界、最近调用、成功率以及解决了哪些问题。

新建插件时，先选择数据库、VM、存储、网络等领域模板，再描述服务和事件。LLM 可以辅助生成 Manifest、Schema 和 Skill 草案，但不会自动获取凭据或执行权。校验通过后下载完整工程，在沙箱中调试，最后经过审查安装或热重载。

换句话说，LLM 帮大家减少样板工作，团队仍对领域逻辑、风险和验收判据负责。

## 第 12 页｜把上下文、Skill、插件、工具与验证放在同一时间线

每次实际运行都会形成完整 Trace：系统注入了哪些上下文，模型形成了什么结构化决策摘要，匹配和实际调用了哪个 Skill，调用了哪个插件与工具，谁批准了什么差异，执行回执是什么，Verifier 又读到了什么。

事件使用追加写入、脱敏和哈希串联，支持回放、恢复和创建分支；叶子分支可按审计规则删除。界面不展示模型私有思维链，只展示可审计的结构化决策、证据引用和工具结果，这既方便调试，也避免暴露敏感推理内容。

转场：有了统一运行时，各团队的实际开发流程会非常短。

## 第 13 页｜每个团队从完整脚手架开始，只补本域能力

第一步从插件中心下载工程；第二步实现只读 Provider，提供 discover、evidence、verify 和 propose；第三步编写 Skill，写清触发条件、根因证据、回滚和成功判据；第四步登记类型化动作，禁止任意命令；第五步跑合同与闭环测试；第六步通过 Merge Request 合并插件。

验收不看写了多少代码，也不看模型调用次数。每组选择一个真实故障场景，必须做到：取到真实证据、生成可审批差异、执行后同目标回读、通过稳定窗口，最终形成一条“已验证恢复”记录。

对数据库组，可以从连接阻塞或只读探针开始；VM 组可从服务异常和磁盘压力开始；存储组可从容量、路径和挂载开始；网络组可从 DNS、路由、LB 和策略命中开始。

## 第 14 页｜统一合同覆盖不同基础设施，领域逻辑由插件维护

七个领域不是七套 Harness，而是七类 Domain Agent 使用不同插件集合。公共插件负责模型、CMDB、通知、审批、审计和知识；领域插件负责资产发现、证据采集、动作提议和验证。

Kubernetes 的 Ready、日志和 rollout，与数据库的复制延迟、VM 的服务 active、存储的路径可达、网络的链路恢复，指标完全不同；但它们都能映射到同一协议：事实、风险、审批、动作、回读、稳定窗口和成效。

这让专业边界更清楚：平台组不冒充数据库专家，数据库组也不需要维护 Agent 事件系统和审批 UI。

## 第 15 页｜模型、插件和执行器都必须通过生产门禁

企业级能力首先是约束。证据必须满足新鲜度和根因反证；爆炸半径包含资源范围、依赖、SLO 和批次上限；策略门禁执行白名单、最小权限和目标冻结；人工审批展示完整差异、风险、回滚和验证标准；写后回读要求同通道、同 UID 或 generation 前进；恢复验证读取真实新状态并跨稳定窗口。

红线很明确：外置插件独立容器、默认只读；不能读取 Secret 明文，不能执行任意 Bash/SQL，不能直接 mutation，也不能绕过审批与 Verifier。失败、超时或证据缺失一律 fail-closed。

因此我们不是因为用了 AI 就降低安全标准，而是利用统一 Harness 把过去散落的安全要求变成默认、可审计、不可绕过的机制。

## 第 16 页｜用实际解决问题，而不是模型调用次数衡量价值

平台成效页应该一眼回答：CISRE 到底解决了什么。核心指标是已验证恢复的问题数、恢复成功率、平均恢复时长、Skill 有效率、审批时延、回滚和复发。点击任一记录可以展开根因、Skill、审批、变更、回读和恢复证据。

对团队的评价也采用同一标准：不是谁注册了最多插件，而是谁把真实故障稳定地解决掉，并把经验沉淀为他人可复用的 Skill。这样指标天然鼓励质量，而不是功能堆叠。

## 第 17 页｜Kubernetes 稳态 → 领域插件 → 规模治理

当前阶段先冻结稳定内核：插件服务可调用、Kubernetes 闭环 5.6.0、Kernel Port v1、275 项回归通过。接下来一到两个月，每个领域认领一个插件和三个高价值 Skills，用真实故障完成核心零改动验收。

二到四个月进入规模化：事务事件存储、分布式租约、持久任务队列和无状态 API/Worker，把单实例语义平滑迁移到多副本。持续阶段则做 Skill 排名、离线评测、合规报表和成本治理。

每个阶段的退出标准都是恢复证据，而不是完成了多少页面或接了多少 API。这能保证路线图始终围绕业务价值。

## 第 18 页｜共建请求

今天希望形成三个具体决定。第一，每个相关团队指定一名 Plugin Owner，负责领域合同、版本、安全和兼容性。第二，以一个插件加三个 Skills 的规模启动试点，不改核心，直接从脚手架独立迭代。第三，用一个真实故障验收，只有恢复成功才计入共同成效。

我们不需要每个组再造 Agent Loop、模型网关、审批、Trace、事件存储、权限和前端。CISRE 已经把这些共同难题做成企业 Harness；大家最宝贵的投入，是把本领域真正有效的经验放进插件和 Skills。

结束语：让我们把个人救火经验变成组织能力，让基础设施能够自解释、可安全自愈、可证明恢复。CISRE 核心由平台共同守护，领域能力由各团队共同拥有。
